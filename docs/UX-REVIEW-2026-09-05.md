# Conway interaction and usability review

Date: 2026-09-05

Status: Expert review complete. Recommendations are proposals, not implementation decisions.

## Scope and method

This review examines Conway's product model, planning and execution workflows,
information architecture, layouts, controls, visual language, accessibility,
and user documentation. Evidence comes from the current application source,
feature specifications and guides, with browser observations identified
separately. This is an expert review, not a user study or a claim that every
runtime path has been tested.

The local application endpoint was unavailable and the Docker daemon was not
running. A static browser inspection can assess shipped layouts and help
content; it cannot establish that authenticated planning or Jira integration
works end to end.

## Initial synthesis

Conway's strength is its constraint-aware decision model: capacity, dependency
order, competing dates, explicit assumptions, tradeoffs and immutable baselines.
The central UX opportunity is to turn that model into an obvious working
routine: understand the situation, prepare a plan, resolve conflicts, agree a
baseline, then review execution and decide what to change.

My assessment: the product can support sophisticated, facilitated planning
today, but independent users must learn too much of its internal model before
they can confidently make ordinary decisions. The visual foundation is usable;
the greater obstacles are unclear state, competing terminology, fragmented
workflows, and incomplete execution feedback. A cosmetic redesign alone would
not address these obstacles.

## Product understanding

Conway is a decision-support product for organizational flow. Its core objects
are teams/pods, capacity tracks, dependency networks, initiatives, period plans,
model assumptions, saved baselines, imported snapshots and learning games.

| Surface | Inputs and purpose | User's essential question |
|---|---|---|
| Measure | Selected Jira-derived snapshot: dependencies, work in progress, cycle times and data quality | Where are we waiting, and how reliable is this picture? |
| Feature Simulator | Task graph and size assumptions, using imported cycle-time distributions | Under these assumptions, how likely is this feature to finish by a date? |
| Plan | Submitted roster, initiative estimates, dependencies, priorities, dates and capacity/calendar assumptions | What fits, in what order, and what must change? |
| Baselines | Immutable saved schedules and their inputs; current-to-baseline and pairwise comparisons | What did we agree, and how has the proposal changed? |
| Learn | Facilitated scenarios, constrained actions, rounds, consequences and debriefs | Which interventions improve overall flow? |

The Go server owns the finite-capacity planning computation and persistence;
the vanilla JavaScript/D3 frontend presents several views of the same result.
Postgres is required. Role gating distinguishes managers, facilitators,
administrators and players. Bootstrap, local fonts and shared tokens already
provide a foundation for consistent controls. These architectural choices
support incremental UX improvements without replacing the frontend stack.

Sources: `README.md:23`, `README.md:35`, `app/js/data.js:1`,
`app/js/auth.js:27`, `docs/COMPONENTS.md:3`,
`server/main.go:354`, `specs/001-plan-execution-order.md:11`.

The critical distinction is that Plan schedules supplied estimates. It does
not automatically turn every planned initiative into a history-calibrated
forecast or an actual-delivery tracker. The model must remain visible enough
that users understand what kind of answer they are receiving.

## What should be preserved

- The scheduler explains binding constraints instead of presenting unexplained dates.
- Optimization proposes an order that a person explicitly accepts.
- Remedies disclose consequences for other initiatives, making tradeoffs discussable.
- The same computed schedule feeds Order and Timeline.
- Baselines preserve the agreement and expose input divergence.
- Upload preview, named drag conflicts and undo already reduce some editing risk.
- Role-aware entry points, demo data, contextual definitions and printable reports provide useful scaffolding.
- The manual explains both purpose and expected results, and the game includes a debrief.

These are product strengths, not a statement that every path was exercised.

## Prioritized findings

Priorities reflect decision risk and task obstruction, not estimated development
effort. P1 should precede broader polish; P2 improves routine task completion.
Independent reviews were challenged by a separate verifier; the findings were
deduplicated and ordered by stable IDs and priority in code.

### F01 · P1 · Distinguish execution from changing a proposal

**Evidence.** Actuals and variance are specified in
`specs/001-plan-execution-order.md:432`, but explicitly deferred in
`specs/004-spec-001-cleanup.md:222` and outside the health report's scope at
`specs/013-plan-health-report.md:191`. The Plan route dispatch at
`server/planhandlers.go:170` has no actuals/variance route. Meanwhile,
`app/js/baseline.js:83` describes actuals against the active baseline, and
`app/docs.html:161` teaches input divergence as checking whether reality drifted.

**Impact.** A user can mistake a new estimate, reordered work or a changed
roster for evidence of delivery progress. Re-baselining can then obscure the
question they originally wanted to answer: did the team deliver what was agreed?
Existing baseline comparison is useful and should be retained; actuals are a
deferred capability, not a newly discovered regression.

**Recommendation.** Introduce three explicitly named states: **Agreed baseline**,
**Working plan**, and **Observed execution**. Immediately correct copy that
implies unavailable actuals. Build the execution workspace as a separate,
specified feature using the existing snapshot pipeline. Include snapshot date,
initiative-to-epic mapping coverage, inferred versus observed starts, completed
dates, remaining-work forecast, and both schedule and estimate variance.

Every exception should end with an accountable next step: owner, action,
review date and decision rationale. Preserve the previous agreement when a new
one is approved. A green state must never result merely from saving a new baseline.

### F02 · P1 · Separate target risk from period fit

**Evidence.** `app/js/report.js:34` counts all non-good verdicts as outside the
period; `server/planning/schedule.go:2112` evaluates lateness against a target.
A direct execution of the report function reproduced the issue: a week-5
target, week-6 finish and 26-week horizon produces “will not finish inside the period.”
See the evidence log below.

**Impact.** A planner could defer work that fits the period when the actual
decision is to renegotiate an earlier target. Correct data in detail does not
repair a misleading headline used in a meeting.

**Recommendation.** Present separate statements: “1 target at risk,” “All 3
initiatives fit the period,” and, where applicable, “2 initiatives need more
information.” Do not infer period fit from the lateness label alone. Keep
unknown future verdicts visible as unknown; do not automatically classify their
specific scheduling consequence.

### F03 · P1 · Unknown and failed checks need visible states

**Evidence.** When pods exist, `app/js/home.js:71` can fail to obtain a dated
plan; missing hygiene produces a null score at `:21`. If no other alert exists,
`:110` nevertheless says dates hold and data is usable. The empty-org screen,
synthetic-data badge and dash-valued quality tile are existing safeguards, but
do not qualify this headline. `app/js/home.js:19` and `:103` also call load of 85% or
more “over capacity,” unlike the report's separate 85%/100% thresholds.

**Recommendation.** Use explicit **Checked**, **Unknown**, **Stale**, **Loading**
and **Could not check** states. For example: “No date risks found in Portfolio
plan. Data quality has not been checked.” Name the plan, snapshot and last
successful check. Say “Approaching capacity” at the warning threshold and
“Over capacity” only when the metric supports it.

A related source concern appears in `app/js/hygiene.js:45`: issue totals come
from a lazily populated issue cache and default to zero. Treat absent aggregate
data as not loaded; fetch org totals independently of drill-downs. This path
was source-inspected, not exercised against Jira in this review.

### F04 · P1 · Make editing state and failure visible

**Evidence.** Timeline drops persist edits at `app/js/planui.js:1014` and
`:1047`, as required by `specs/008-drag-edit-timeline.md:111`. Undo is one-level
state (`app/js/planui.js:21`, `:134`). Yet `app/docs.html:159` calls dragging a way to
try a change without committing. The baseline stays immutable and the manual
later warns about changed inputs; persistence itself is intentional.
Separately, accepting an order can return silently on failure
(`app/js/planui.js:1481`), while pin failure feedback is placed in a title (`:1364`).

**Recommendation.** Make “Working plan · autosaved” unmistakable and offer a
separate named scenario or duplicate-plan workflow for multi-step experiments.
Use specific verbs: **Save settings**, **Save initiatives**, **Apply proposed
order**, **Save agreed baseline**. Every write needs visible pending, success
or error feedback next to its initiating action. Retain user input on failure.

Dragging an edge changes an estimate, not merely a picture. Show that meaning
before the user drops: “Estimate 4 → 3 weeks.” Offer a visible Undo action and
precise editing controls; a keyboard shortcut alone is insufficient guidance.
Longer undo history would make exploration more forgiving.

### F05 · P2 · Lead with a decision and preserve context

**Evidence.** Populated plans default to Network (`app/js/planui.js:354`).
The stronger verdict-first presentation exists in Order (`app/js/order.js:436`).
Plan horizon/loss/Save remain above the collapsed setup disclosure
(`app/js/planui.js:230`), despite the results-first intention of
`specs/009-planning-ia-pass-2.md:17`. Main view changes use CSS state
(`app/js/main.js:216`); plan identity is held in module memory (`app/js/planui.js:204`).

**Recommendation.** Default a new populated plan to a concise review: period
fit, target risks, missing inputs, primary constraint and next decision. Return
experienced users to their last view. Keep Network as an explanation of
dependencies, rather than the first thing every planner must decode.

Add permission-aware URLs for plan, view, selected initiative and filters.
Browser Back, refresh and copied links should restore the task context.
Same-page app switching already retains the plan, and snapshots already have
URL support; extend those strengths. Do not describe all existing navigation
as state-losing.

### F06 · P2 · Turn remedies into reviewable actions

**Evidence.** `app/js/remedyui.js:54` renders costs and affected initiatives,
but does not offer a remedy application flow. The health report routes back
to full options (`app/js/report.js:119`).

**Recommendation.** Each recommendation should offer **Preview this change**.
Show current/proposed finish, affected commitments, capacity assumptions,
scope removed and remaining risks. Then explicitly apply to the working plan.
Organizational actions such as staffing transfers need an owner and acceptance;
do not imply that a simulation has moved real staff or changed Jira.

Replace an isolated “portfolio objective −12” with the decision first:
“Rescues Atlas; moves Beacon one week later.” Keep the score and dispatch rule
available in details. Distinguish feasible relief from an option that merely
removes a date constraint.

### F07 · P2 · Make the timeline readable without decoding it

**Evidence.** Order uses `wN` dates (`app/js/order.js:156`, `:183`); calendar
dates on timeline ticks are tooltip content (`app/js/timeline.js:213`). The
filter changes meaning with lens (`app/js/timeline.js:575`) and resets on lens change
(`app/js/planui.js:1105`). Several critical labels and actions use 10–12px
type (`app/css/style.css:400`, `:419`, `:520`, `:541`).

**Recommendation.** Show calendar dates when a period start exists, with week
numbers secondary. Keep **Initiative** and **Team** filters separate and
persistent; grouping by team should change the presentation, not the filter's
meaning. Display active filters and result counts.

Give timeline selection a persistent inspector: start, finish, target, buffer,
binding constraint and a precise edit form. Preserve the target diamond,
buffer tail and text statuses, with a compact nearby legend. Distinguish
historical agreement, current schedule and actuals with both styling and labels
once actuals exist. Do not overlay all three by default.

Keep initiative names readable, show full names in the inspector, and provide
sticky labels and time context for long plans. At narrow widths, prefer an
exception list or team work list. Keep dense timeline analysis available as a
deliberate larger-screen mode.

### F08 · P2 · Make help accurate, navigable and contextual

**Evidence.** Seven task-reference links at `app/docs.html:157` through `:164`
have `data-anchor` without native `href` or iframe-local handling. The sidebar
uses working anchors. The iframe Escape handler references an out-of-scope
`ov` (`app/js/docs.js:35`). These two behaviors were also observed in the
browser. The manual hides its contents sidebar below 1101px
(`app/docs.html:41`) without replacement; the sidebar was absent in the narrow
embedded inspection.

The introduction describes history-based forecasting without guessed durations
(`app/docs.html:78`), while Plan explicitly needs uploaded weeks (`:330`).
Directions still reference Observe/Train (`:156`, `app/js/guide.js:347`) while
the app uses Measure/Learn (`app/index.html:33`, `:53`). Separate Docs and Guide
controls (`:59`) open different help experiences; Guide defaults to Executive
(`app/js/guide.js:334`).

**Recommendation.** Repair native anchors and Escape behavior first. Consolidate
help under **Help**, with **Help with this screen**, **First plan walkthrough**,
**How do I…?** and **Glossary**. Offer a persistent contents selector and search
at smaller sizes. Keep the work visible alongside short contextual help; open
the full manual when requested. Remember the selected persona.

Explain the three model types near the start. Name the source of each date.
Label simulated P85 as conditional on the data and assumptions, rather than a
guarantee or automatic instruction to commit. Replace claims such as “85%
means already late” with calibrated risk language. Make actuals coverage and
unavailable capabilities explicit.

## Layout and visual language

### A clearer planning workspace

The recommended hierarchy is:

1. **Context:** plan name, period, working-plan save state and active agreement.
2. **Answer:** separate period fit, date risks and missing evidence.
3. **Work:** a sortable initiative list or timeline, preserving selection.
4. **Inspector:** why the selected item is at risk and its next action.
5. **Details on demand:** model assumptions, technical scoring and setup.

A manager should be able to answer “what needs a decision?” in the first
viewport. A team lead needs a different default: ready work, blocked work,
incoming dependencies and this week's handoffs. An executive needs exceptions,
choices and their consequences. A facilitator needs session purpose, readiness
and the next round action. These are views of shared evidence, not separate
copies of the data. A new team-lead landing is a product proposal; current
permissions would need an explicit design decision.

Use one primary action per decision context. Avoid making settings, export,
optimization and baseline creation equally prominent. Preserve the Bootstrap
and token foundation; standardize components incrementally. The existing app
shell still brands everything “Flow Game” (`app/index.html:5`, `:25`), which
undersells planning and can mislead staff. Use Conway with a planning/flow
descriptor; keep Flow Game inside Learn.

The static narrow screenshot showed the header continuing beyond the visible
right edge. `app/css/style.css:6` and `:16` use a nonwrapping header/nav, and
`app/index.html` has no viewport meta tag. Add responsive navigation and a
viewport declaration, then test all role combinations. Do not simply shrink
the type to accommodate more buttons.

### Icons and buttons

The current mixture of emoji, text glyphs and symbols is apparent in the
navigation (`app/index.html:39`), toolbar (`app/js/planui.js:267`) and controls.
Replace it with one restrained SVG icon family consistent with the installed
design system. This is a consistency change, not a recommendation to replace
domain chart symbols.

| Meaning | Suggested icon concept | Visible label |
|---|---|---|
| Edit an initiative | Pencil | Edit initiative |
| Adjust model inputs | Sliders | Assumptions |
| Compare proposals | Comparison arrows | Compare changes |
| Save an agreement | Bookmark/check | Save agreed baseline |
| Hold priority | Pin | Pin priority |
| Set a start constraint | Calendar/lock | Lock start |
| Print/share a report | Document/export | Export report |
| Obtain help | Circle question | Help |

Pinning rank, locking a date and freezing a baseline are different acts and
should not share a generic lock metaphor. Use icons with text for unfamiliar
actions. Icon-only controls need accessible names. Preserve text and shapes
alongside green/amber/red statuses. Reserve “baseline” for the saved agreement;
the network's no-lever comparison currently also uses the word
(`app/js/planui.js:1868`). Call that state **Current inputs**.

Prefer outcome-oriented labels: **Forecast completion** over **Run 10,000
trials**; **Why this start?** over **Binds**; **Constraint team** with “drum” in
help; **Finish with buffer** instead of an unqualified promise. Continue using
expert terminology in the explanatory layer for users who need it.

### Accessibility and dense-work usability

The app already has button focus styling (`app/css/style.css:347`), native
form adoption (`app/js/forms.js:1`) and accessible glossary buttons
(`app/js/terms.js:142`). Extend these patterns consistently. Sortable table
headers currently have click delegation without keyboard/sort-state semantics
(`app/js/sortable.js:40`). Use buttons in headers with `aria-sort`, clear labels
on login and editing fields, and status announcements for asynchronous changes.

Provide non-drag controls for moving, resizing and assigning lanes; the existing
initiative editor is a useful starting point but does not establish parity for
every gesture. Check dialog focus containment, Escape and return-to-invoker in
the actual workflow, not just framework comments. Essential explanations must
be reachable by keyboard and touch rather than hover only.

Adopt WCAG 2.2 AA as a validation target: normal text contrast, visible and
unobscured focus, keyboard access, non-color cues, and 24 CSS-pixel minimum
targets or qualifying spacing/exceptions. Prefer roughly 44px touch controls
where practical. This review does not claim measured contrast failures or
overall conformance. Source: [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/),
accessed 2026-09-05.

## Make the planning and execution routine explicit

### First planning session

Offer **Try the demo** and **Create my plan** without making Jira import appear
mandatory for planning. Use a short completion checklist: roster matched,
initiatives validated, period set, estimate units understood, assumptions
reviewed. Existing upload preview should show row-level errors, unmatched teams
and a small before/after sample. Correct data before making it look authoritative.

For model choices, use a worked example: “10 effort-weeks across 2 tracks is
about 5 calendar weeks before loss and other constraints.” Ask what the sheet's
numbers mean. Do not make users select a mathematical model before they can
recognize their own estimating practice. Keep scoring, splitting and advanced
dispatch details collapsed.

### Planning review

Read the portfolio answer, select the largest risk, understand its constraint,
preview a remedy, inspect displaced work, apply a chosen proposal, then save
the agreement with a rationale. Let people reject the engine's recommendation
without treating the plan as erroneous.

### Weekly execution review

After the actuals feature is implemented, provide this sequence:

1. Refresh observations; report freshness and initiative mapping coverage.
2. Compare current evidence with the active agreement.
3. Review exceptions: late handoffs, blocked work, changed scope, unstarted priorities and weakening forecasts.
4. Choose an intervention; name its owner and expected effect.
5. At the next review, check whether the intervention reduced delay or improved delivery.

Do not turn this into another manually maintained task tracker. Reuse Jira
issue links and snapshots, and store the planning decisions that Jira does not
already capture. Separate lack of evidence from poor performance. Avoid ranking
teams as intrinsically good or bad from utilization or throughput alone.

### Learning sessions

Preserve the scenario/game/debrief loop. Begin facilitator setup with learning
purpose and available time, then offer a suitable preset. Expand “AP” to
“Action points per round” and “timer s” to a human-readable duration
(`app/js/gamesui.js:17`). Explain what each preset teaches. In the debrief,
connect an intervention to a planning question: “Which commitment improved,
what else moved, and would this constraint exist in your organization?”

## Documentation structure

Organize user guidance by jobs, with theory and reference supporting them:

| Guide | Essential content |
|---|---|
| Make a first plan | Safe demo, inputs, expected result, one small change, undo, save agreement |
| Decide whether to commit | Period fit versus target risk, forecast assumptions, tradeoffs |
| Resolve a conflict | Select the constraint, compare options, inspect affected commitments |
| Review execution | Current capability boundary; later, refresh, mapping, variance and decisions |
| Run a planning meeting | A short agenda and printable decision record |
| Run a learning session | Setup by purpose, participant instructions and debrief |
| Reference | Terms, import columns, model assumptions, roles and troubleshooting |

Each recipe should identify its starting screen, steps, expected result and
recovery path. Use generic annotated examples and repeatable demo data. Make
UI names and help destinations part of the same maintained vocabulary.

Separate operator/developer setup in README and deployment guides from the
planner's usage guide. Mark prototype and future architecture documents as
historical/proposed where appropriate; an implementer should not infer current
capabilities from an aspiration. Review active specs against UI changes rather
than allowing the manual to become a second specification.

## Implementation sequence and success criteria

| Sequence | Scope | Completion criterion |
|---|---|---|
| First: trust and blockers | F02/F03, visible write errors, manual anchors/Escape, truthful model/actuals language | The reviewed counterexamples produce accurate states; keyboard users can navigate and leave help |
| Next: daily usability | Decision-first landing, consistent action labels/icons, explicit saved state, dates, filters, responsive shell and resumable URLs | A new planner identifies the main risk, edits a proposal and compares it with an agreement without coaching |
| Then: safe decisions | Remedy previews, named scenarios, clearer change review and decision capture | Users can explain both the benefit and affected commitments before applying a change |
| Product feature: execution | Complete and validate the deferred actuals/variance contract | Each exception has traceable evidence; unknown mapping/freshness remains visible; re-baselining preserves prior agreements |

These are sequencing recommendations, not delivery estimates. The execution
workspace needs source access and explicit requirements; it should not be
treated as a small layout adjustment.

Run a formative study with 5–8 representative planners, team leads and
facilitators, then repeat after changes. Proposed targets, to establish against
an observed baseline: identify the main risk and its cause within 60 seconds;
complete a first demo plan and explain its commitment in 15 minutes; correctly
distinguish a target miss, a period overrun and unknown evidence; perform a
multi-step what-if without accidentally changing the agreement; complete the
same essential workflow with keyboard only. These are proposed usability
criteria, not measured results.

Existing analytics track adoption and activity (`specs/016-usage-analytics.md:17`).
Augment them with task outcomes: input corrections, successful comparison,
recovery from errors, scenario acceptance/rejection and return to a decision.
Do not treat schedule computation counts as proof that planning improved.
Evaluate delivery outcomes over multiple review cycles: earlier risk discovery,
fewer unplanned starts, resolved handoff delays and forecast calibration when
actuals become available.

The review follows established principles of visible system state, recognition
over recall and help tied to tasks. Source:
[Nielsen Norman Group usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/),
accessed 2026-09-05. The specific recommendations above are judgments based on
Conway's source and observed help interface, not findings from a Conway user study.
